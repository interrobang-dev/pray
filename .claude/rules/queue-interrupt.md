# mod·입력 제안·곁가지 질문·대기열·작업 중지

웹 세션에만 불러오는 mod(입력 제안·입력칸 알림·곁가지 질문 `/jk-btw`), 보내기의 함정, 작업 중 보낸 메시지의 대기열, 대기 메시지 취소, 작업 중지(Esc)를 다룬다.

원래 루트 `CLAUDE.md` 한 파일이던 내용을 옮긴 것이다. 본문의 "위·아래 …"·"핵심 개념 …" 은 그때의 말이라 가리키는 항목이 다른 파일에 있을 수 있다. 어디서나 지킬 규칙·근무·휴식·퇴근·표시 상태·실행 방법은 루트 `CLAUDE.md`, 다른 영역은 루트의 문서 지도를 본다. 이 영역을 고치면 이 파일의 그 줄을 고쳐 쓴다.

다른 파일에 있는 항목:
- 대화 탭의 [Cancel]·[Stop] 화면 → chat.md
- API 경로 목록 → server-api.md
- 곁가지 질문 카드 화면(`BtwCard.tsx`·입력칸 `/btw`) → chat.md

## 구조

- `mod/` — 웹 세션에만 불러오는 Claude Code mod (plugin 이름 `pray`, 빌드 없음: 엔진이 .ts 를 직접 읽는다). `.claude-plugin/plugin.json` 매니페스트, `hooks/hooks.json`(`{"modules":["./register.ts"]}`), `hooks/register.ts` 훅 모듈(`prompt.suggest` 에서 `next(e)` 결과가 `isShown` 이면 그 글을, `prompt.submit` 에서 null 을 `POST http://127.0.0.1:4710/api/hook/suggestion` 으로 보낸다. `prompt.change` 에서 origin `engine`(↑ 로 대기열 꺼냄·응답 전 중지로 글이 돌아옴 등)·자기 fill(origin `plugin`, name `pray`)·빈 입력칸인 변경만 `POST /api/hook/prompt-box` `{ sessionId, text, origin }` 으로 알리고, 2초 안에 온 답에 `fill` 이 있으면 `$.prompt.fill({ text, mode: 'replace' })` 만 한다 — 아래 대기 메시지 취소·작업 중지. 곁가지 질문: `session.start` 에서 `/jk-btw` 를 `immediate: true` 로 등록하고 `command.describe` 로 typeahead·/help 에서 숨기며, `command.run` 이 요청 ID 를 받으면 질문을 GET 해 `$.model.fork` 결과를 POST 한다 — 아래 곁가지 질문), `tests/suggest.test.ts`·`tests/prompt-box.test.ts`·`tests/btw.test.ts`(가짜 엔진 시험 4개·5개·6개. `prompt.change` 는 엔진만 올리는 이벤트라 타입의 `$` 에는 없지만 시험 엔진의 `$.prompt.change` 로 올릴 수 있다). 검사는 `claude plugin validate mod`(README·LICENSE 없음은 plugin directory 제출 검사라 해당 없음)와 `claude plugin test mod`. 엔진이 불러올 때 `.claude-plugin/types/`(API 타입·tsconfig)를 만드는데 그 안의 `.gitignore` 가 `*` 라 커밋되지 않는다
- `server/src/suggestion.ts` — 제안 요청 검증·반영 `applySuggestion` (순수): 호스트 목록(웹 세션)에 없는 ID 는 무시, 글은 trim·1000자에서 자르고 비면 지움
- `server/src/btw.ts` — 곁가지 질문의 순수 함수·저장소: 질문 검사(1~4000자, trim), mod 가 보낸 fork 결과 → 답·화면 실패 문구(`parseBtwResult`: nothing-to-fork·api-error·empty-reply·aborted), 세션별 문답 `BtwStore`(최근 20개, pending → answered·failed 한 번만, mod 에 줄 이전 문답 = 그 질문 앞의 answered 것). 실측 결과가 파일 머리 주석에 있다. 라우트는 `index.ts`(→ server-api.md)
- `server/src/unqueue.ts` — 대기 메시지 취소의 순수 함수: 입력칸 알림에 대한 답·단계(`answerBox`: popping → filling ⇄ submitting → done, 남길 글이 없으면 clearing, 기대와 다른 글이면 stuck), ↑ 이후 jsonl 판정(`judgeQueue`), 둘을 합친 결과(`decideOutcome`)
- `server/src/interrupt.ts` — 작업 중지의 순수 함수: 중지 줄 판별(`isInterruptText`), Esc 이후 jsonl 결말(`judgeInterrupt`: 중지 줄 = stopped, 그 사이 dequeue 가 있으면 continued), Esc 때 차례가 아직 응답을 안 남겼는지(`isAwaitingFirstResponse`), 중지 중 입력칸 알림에 대한 답(`answerInterruptBox`: 처음 온 engine 변경 = 돌아온 글을 기억하고 `{ fill: '' }`, 그 뒤 자기 fill 의 빈 입력칸 = 비움 확인), 셋을 합친 결과(`decideInterrupt`: 기록이 없는데 응답 전이었거나 돌아온 글을 비웠으면 restored, 아니면 unknown). 실측 결과가 파일 머리 주석에 있다

## 핵심 개념

- **다음 입력 제안(Claude Code "Prompt suggestions")은 jsonl·훅에 없고 mod 의 `prompt.suggest` 훅으로만 얻는다** (추가 API 호출 없음). 이 훅은 엔진 자체 제안에도 불리고(origin `suggestion`), `next(e)` 결과 `{ isShown }` 이 true 일 때만 실제로 입력칸에 놓인 것이다. 제안이 사라지는 이벤트는 없어서 `prompt.submit`(슬래시 명령·숨은 프롬프트 포함)에서 null 을 보낸다 — 그래서 터미널에서 직접 치기 시작해도 제안 버튼·말풍선은 보낼 때까지 남는다. 세션 키는 호스트가 넣는 `PRAY_SESSION`(`sessionIdOf`. 호스트를 재시작하기 전 옛 웹 세션을 위해 없으면 옛 이름 `JK_CORP_SESSION` 을 읽는다 — `$.env.get` 은 글자 그대로의 이름만 받아 두 번 부른다. 호환 코드) (`/clear` 하면 `$.session.id()` 가 바뀌어서). 이 변수가 없으면(외부 세션) 아무것도 안 한다
- **mod 는 웹 세션에만 불러온다**: 호스트가 자식 env 에 `CLAUDE_CODE_PLUGIN_DIRS` 를 넣는다 (여러 개면 Windows 구분자 `;`. 승인 창 없음). 터미널·IDE 에서 띄운 claude 는 불러오지 않는다. **반영: 처음 한 번은 호스트 재시작**이 필요하다 (웹 세션이 새 env 로 `--resume` 돼야 mod 를 불러온다). 그 뒤 `mod/` 를 고쳐 저장하면 모든 웹 세션이 바로 다시 불러온다 — 깨진 코드는 그 세션들 대화에 흐린 오류 줄(`pray: …`)을 남기므로 고친 뒤 `claude plugin validate mod`·`claude plugin test mod` 를 먼저 돌린다
- **mod 의 `$` 규칙** (엔진이 검사한다): `$` 는 파일 최상위에 선언한 함수에만 넘길 수 있다 (`post` 가 `register` 밖에 있는 이유). env 변수 이름은 문자열 리터럴이어야 한다. `$.http.fetch` 는 localhost 를 막지 않지만 기본 타임아웃이 30초라 훅에서 기다리지 않는다 (`void` + 함수 안 try/catch. 기다리면 서버가 멈췄을 때 제출이 늦어지고, 훅이 던지면 대화에 흐린 오류 줄이 남는다). 답이 필요하면 그 `void` 함수 안에서 `$.clock.sleep` 과 `Promise.race` 로 기다림을 자른다 (`reportBox`. `HttpInit` 에는 타임아웃·signal 이 없다). 주소는 IPv6(`::1`)로 가지 않게 `127.0.0.1`
- mod API 는 early access 라 Claude Code 업데이트로 바뀔 수 있다. 깨지면 제안 버튼·말풍선만 안 뜬다 (세션은 그대로, 대화에 흐린 오류 줄). 엔진이 제안을 아예 안 만드는 때가 있다: 터미널 포커스가 빠졌을 때, 프롬프트 캐시가 식었을 때, 사용량 한도 근처, plan 모드, 제안을 20번 연속 안 쓰면 그 뒤로는 10번에 1번만 등
- **곁가지 질문 (웹 세션만, Claude Code `/btw` 와 같은 일).** 지금 대화 문맥으로 도구 없이 한 번 답하고, 문답은 대화 기록(jsonl)에 남지 않고, 작업 중에도 차례를 멈추지 않는다. 내장 `/btw` 는 터미널 오버레이라 답을 jsonl·훅으로 얻을 수 없어 mod 의 `$.model.fork` 로 직접 만든다. 흐름: 화면 `POST /api/sessions/:id/btw { question }` → 서버가 요청(UUID)을 만들고 pty 에 `/jk-btw <요청 ID>` 를 쓰고 300ms 뒤 ``(보내기의 함정과 같은 이유. 응답은 Enter 뒤라 화면의 보내기 줄과 섞이지 않는다) → mod `command.run` 이 `{}`(글 없음)로 바로 끝내고 따로 `GET /api/hook/btw/:requestId?sessionId=` 로 `{ question, history }` 를 받아 `$.model.fork({ prompt })` → 결과(ModelForkResult 그대로)를 `POST` → 서버가 저장하고 SSE `btw`. prompt 는 **내장 /btw 의 system-reminder 문구 그대로**(2.1.311 바이너리에서 뽑았다: "This is a side question … You have NO tools available …") + 이전 문답(`<side_question>`·`<side_answer>`, 오래된 것 먼저. 내장은 따로 된 메시지로 넣지만 fork 는 prompt 하나라 글로 넣는다) + 질문. fork 는 main 의 마지막 요청(모델·시스템 프롬프트·도구·메시지)을 다시 보내 프롬프트 캐시를 읽고 도구는 모두 거부된다. 요청 ID 꼴(UUID)이 아니면(사람이 터미널에서 직접 친 `/jk-btw`) 아무것도 안 한다. **실측 (Claude Code 2.1.311, Haiku, node-pty + 포트만 바꾼 mod 사본 + 가짜 서버)**: 쉬는 중 약 2초, Bash 실행 중 약 3초에 답이 오고 차례는 멈추지 않고 원래대로 끝났다(Stop "done"). `/jk-btw` 를 친 흔적은 jsonl 에 한 줄도 없고(명령 줄·출력 줄 모두) 다음 차례 claude 에게 "jk-btw 가 든 메시지가 있나" 물으면 "no" — 그래서 `messages.ts` 는 고치지 않았다. 화면에도 출력 줄이 없다. usage: 쉬는 중 첫 fork cache_read 51,882·creation 4,807, 작업 중 fork cache_read 56,689·creation 0. 첫 차례가 끝나기 전에는 `nothing-to-fork`. 내장 `/btw` 와 이름이 안 겹치고(`btw` 는 등록이 거절되는 내장 이름) 숨겨서 typeahead 의 `/btw`·`/jk` 에 `/jk-btw` 가 안 보인다 (숨기기 전에는 `/btw` 를 치면 둘째 줄에 보였다). 사람이 친 `/jk-btw`·`/jk-btw hello` 는 서버에 요청 0개·화면 변화 없음. **한계**: 작업 중 fork 는 main 의 마지막 *요청*까지만 보아 그 뒤의 도구 호출(지금 도는 Bash 등)을 모른다 ("지금 뭐 해?" 에 엉뚱하게 답했다 — 내장 /btw 는 진행 중 메시지와 "결과 없음" 도구 결과를 더해 이것을 안다). `/jk-btw` 제출에도 `prompt.submit` 이 돌아 입력칸 제안이 지워진다. 입력칸(터미널 탭)에 쓰던 글이 있으면 명령 글이 그 뒤에 붙어 보통 메시지로 제출된다 (화면 보내기와 같은 함정)
- **보내기의 함정 (대화 탭).** pty 쓰기를 짧은 간격으로 이으면 claude 가 한 read 로 합쳐 받아, 마지막 `\r` 이 앞 글과 같은 덩어리에 섞이면 제출 대신 줄바꿈이 된다 (줄마다 따로 보내면 4줄 이상이 거의 막혔다). 800자를 넘는 덩어리는 Claude Code 가 붙여넣기로 처리하고, 그 글에 그림 확장자(png·jpg·jpeg·gif·webp)로 끝나는 경로가 있으면 `[Image #N]` 으로 바꾼다 — 경로를 백틱으로 감싸면 안 바뀐다(실측). 800자 넘는 글은 jsonl 에 `<pasted_content>` 로 감싸여 남지만 `messages.ts` 가 풀어 원문과 같아진다. 글이 `\` 로 끝나면 `\`+Enter 가 줄바꿈이라 제출되지 않는다 (고치지 않은 기존 문제)\n- 채팅 뷰는 별도 API 없이 **터미널 키 입력**으로 지시를 보낸다. 슬래시 명령은 자동완성이 Enter 를 먼저 먹어 두 번 눌러야 할 수 있다
- **작업 중에 보낸 메시지는 `type: user` 로 남지 않는다.** 보낼 때 `queue-operation` `enqueue`(글만, uuid 없음), 차례 중간에 받아들이면 `remove`(reason `absorbed_mid_turn`) + `attachment.type: queued_command` 줄(서버가 그 위치에 user 로 넣는다. timestamp 는 보낸 시각), 차례가 끝난 뒤 받으면 글 없는 `dequeue` + 일반 user 줄이 남는다. 빈 입력칸에서 ↑ 로 입력칸에 꺼내면 꺼낸 것마다 `popAll`(글 있음, reason 없음. 하나만 꺼내는 `popOne` 은 기본 꺼짐)이 남는다. 짝이 아직 없는 enqueue 는 대화 맨 끝에 `isQueued: true`(id `queued-<줄 번호>`)로 붙인다. 짝 맞추기: remove·popAll·popOne 은 이유(취소 등)와 관계없이 글이 같은 것 중 먼저 들어온 것을, dequeue 는 바로 뒤(다음 queue-operation 전)에 claude 가 받은 글(user 줄·queued_command)과 같은 것을, 없으면(슬래시 명령·글 없는 enqueue) 맨 앞을 뺀다 — Claude Code 는 우선순위(now/next/later) 순으로 빼지만 jsonl 에 우선순위가 없어서다 (우선순위가 다른 것이 함께 대기하면 틀릴 수 있다). 글 없는 enqueue 는 순서용으로만 세고 화면에 안 낸다. task-notification 첨부도 같은 규칙이라 system 으로 보인다
- **대기열은 claude 프로세스 메모리에만 있어 프로세스가 끝나면 사라진다.** 그래서 `cost-state` 줄에서 대기열을 비운다 — Claude Code 가 프로세스가 세션을 떠날 때(종료·kill·호스트 재시작·세션 전환) `cost-state` · `last-prompt` · `cost-state` 로 남기는 줄이고 정상 진행 중에는 안 나온다 (jsonl 164개에서 파일 중간에 나온 38곳 모두 그 뒤에 새 프로세스의 `SessionStart:resume` 이 왔다). 다시 뜬 프로세스는 못 받은 백그라운드 알림을 `<status>stopped</status>` 알림으로 새로 enqueue 한다 (Claude Code 도 그 전 enqueue 를 없어진 것으로 본다). 안 비우면 죽기 직전 enqueue 가 주인 없이 맨 앞에 남아 그 뒤 dequeue 가 한 칸씩 밀리고, 가장 최근에 받은 것이 늘 "Queued"(대기 취소의 [Cancel]·↑ 까지)으로 보인다. 강제 종료면 `cost-state` 가 없다 (`SessionStart:resume` 앞에 없던 곳 4번) — 그때 남은 항목은 다시 근무하면 대기 중으로 보이지만 dequeue 를 글로 맞추므로 밀리지는 않는다. 새 프로세스 시작에는 Claude Code 가 늘 쓰는 줄이 없다 (`SessionStart` 훅 첨부는 command 훅이 있을 때만 생기고 첫 질의 때 늦게 써진다). 죽는 프로세스가 `cost-state` 뒤에 알림을 enqueue 하기도 한다 (jsonl 166개 중 2곳). 이렇게 jsonl 에 남은 대기 항목 때문에 **messages API 는 근무 중이 아닌(휴식·퇴근) 세션에서 `isQueued` 메시지를 뺀다** — 프로세스가 없으면 대기열도 없다. 대기 취소(`queuedPrompts`·cancel-last)는 근무 중인 웹 세션만 다루므로 거르지 않는다
- **대기 메시지 취소 (웹 세션만).** 대화 탭의 맨 마지막 "Queued" 말풍선에만 [Cancel] 버튼이 붙는다 (claude 가 작업 중이고 승인 대기·질문 중이 아닐 때. Chat.tsx). 누르면 "Cancelling…", 끝나면 대화 맨 아래 가운데 한 줄 "Queued message · cancelled · moved to the input box / already taken by claude / couldn't cancel: check the Terminal tab / failed: check the Terminal tab"(6초. 409 등 거절은 "couldn't cancel: <서버 문구>"). Claude Code 에는 대기열에서 하나만 빼는 방법이 없어서 이렇게 한다: 서버(`POST /api/sessions/:id/queue/cancel-last` `{ text }`)가 웹 세션·working·질문 없음·jsonl 의 마지막 대기 글(`queuedPrompts`)이 text 와 같음을 확인하고, 대기 글 [q1..qn] 을 세션별 메모리에 둔 채 pty 에 ↑(`\x1b[A`)를 보낸다 → 엔진이 대기 메시지를 전부 꺼내 `q1\n…\nqn` 을 입력칸에 넣는다 → mod 가 알린 글이 그것과 정확히 같으면 서버가 q1 을 fill 하라고 답한다 → fill 한 글이 그대로 알려지면 서버가 pty 에 `\r` → 빈 입력칸 알림이 오면 다음 글, q(n-1) 까지. 남길 글이 없으면 `{ fill: '' }` 로 비우기만 한다. 기대와 다른 글이 오면 거기서 멈추고 더 지시하지 않는다(stuck). 꺼냄 알림은 3초, 전체는 10초를 넘으면 상태를 비우고, ↑ 이후 jsonl 을 최대 3초 기다려(`judgeQueue`: 목표 글의 popAll 만 = 취소됨, popAll 과 같은 글의 queued_command = 흡수 중에 꺼내 이미 받음, popAll 없이 remove absorbed_mid_turn·dequeue = 이미 받음) 진행 결과와 합친다(`decideOutcome`). 응답 `{ outcome: cancelled·accepted·stuck·failed }` 은 그때까지 기다려서 몇 초 걸린다. **cancelled 면 화면이 취소한 그 글(말풍선 글)을 웹 입력칸에 넣는다** (서버는 그대로. 아래 "되돌아온 글 넣기"). 진행 중에는 그 세션의 `/input` 이 409 다 (다른 키가 섞이지 않게). `/api/hook/prompt-box` 는 진행 중인 취소가 없으면 `{}` 라 평소에는 아무 일도 없고, suggestion 과 같은 이유로 인증 예외가 아니다. 진행 상태는 메모리에만 있고 exit·호스트 끊김 때 지운다
- **대기 메시지 취소의 함정.** 작업 중 Esc·Ctrl+C 는 차례를 멈춘다 — 입력칸이나 대기열을 다루려고 절대 보내지 않는다 (Ctrl+S 도 쓰지 않는다). ↑ 는 하나가 아니라 **사람이 친 대기 메시지를 전부** 꺼낸다 (입력칸에 쓰던 글이 있으면 `꺼낸 글\n쓰던 글`, 대기열이 비었으면 이전 입력 기록을 불러오고, 여러 줄 초안의 커서가 첫 줄이 아니거나 자동완성 목록이 떠 있으면 다른 일을 한다) — 그래서 나머지를 다시 넣는다. **다시 넣을 때 mod 의 `$.prompt.submit` 을 쓰지 않는다**: 대기열에 들어가긴 하지만 jsonl enqueue 에 글이 없어 "Queued" 말풍선이 사라지고, ↑ 로 다시 꺼낼 수 없고, 차례 중간에 전달되지 않고 차례가 끝난 뒤 따로 돌며(user 줄 origin `plugin`), promise 는 그 차례가 시작돼야 끝난다. 그래서 mod 는 fill 만 하고 Enter 는 서버가 pty 로 보낸다 (사람이 Enter 친 것과 같은 보통 대기 메시지가 된다). 다시 넣은 메시지는 새 enqueue 라 시각이 취소한 때로 바뀐다 (그대로 둔다). ↑ 직전에 받아들여져 대기열이 비면 ↑ 가 이전 입력 기록을 불러오는데 mod 는 기록 불러오기(origin `history`)를 알리지 않아 그 글이 입력칸에 남는다 (결과는 jsonl 로 "already taken by claude")
- **작업 중지 (웹 세션만).** CLI 에서 작업 중에 누르는 Esc 와 같다. 키는 **Esc 한 번**(`\x1b`) — Ctrl+C 는 두 번 들어가면 claude 가 종료된다. 화면은 `/input` 으로 Esc 를 보내지 않고 `POST /api/sessions/:id/interrupt` 만 부른다. 서버는 웹 세션(아니면 404)이 working 이고 승인 대기·질문 중이 아니고(Esc 가 도구 거부·질문 거절이 된다) 대기 메시지 취소·다른 중지가 진행 중이 아닐 때만(아니면 409 + message) pty 에 Esc 하나를 보내고, jsonl 을 최대 3초 지켜봐 `{ outcome }` 으로 답한다 (`interrupt.ts`): **stopped**(중지 줄) → 상태 my-turn, **continued**(중지 줄 + dequeue: 대기 메시지로 바로 다음 차례가 시작됨, 그 차례의 Stop 이 온다) → 상태 그대로, **restored**(기록이 없는데 Esc 때 차례가 아직 응답을 안 남겼거나, 돌아온 글을 비움) → my-turn, **unknown**(기록 없음) → 그대로. **응답 전 중지로 보낸 글이 Claude Code 입력칸에 돌아오면 서버가 그 입력칸을 비우고 글을 넘긴다**: 서버는 Esc 를 보내기 전에 세션별 중지 상태(`interrupts`, 메모리)를 두고, 그동안 `/api/hook/prompt-box` 에 처음 온 engine 변경(돌아온 글)에 `{ fill: '' }` 로 답하고, 자기 fill 의 빈 입력칸 알림이 오면 비운 것으로 보고 jsonl 을 더 기다리지 않고 `{ outcome: 'restored', text: 돌아온 글 }` 로 답한다 (약 0.1초. 비운 것이 확인되지 않으면 text 없이 — 글이 두 곳에 있지 않게). 대기 취소가 진행 중이면 그쪽 상태 기계가 먼저다 (둘은 서로 409 라 겹치지 않는다). 응답 뒤 온 알림은 `{}`. mod 는 고치지 않았다 — 이미 engine 변경을 알리고 답의 `fill` 을 넣는다. 그래서 옛 서버(`{}` 만 답함)와 새 서버 어느 쪽에서도 그대로 돈다
- **되돌아온 글 넣기 (화면).** 중지 응답에 `text` 가 있거나 대기 취소가 cancelled 면 그 글을 웹 입력칸 맨 앞에 넣는다 (`composerDraft.ts` 의 `restoreToComposerDraft` → `ComposerHandle.reload`): 쓰던 글이 있으면 `되돌린 글\n쓰던 글`(↑ 로 꺼낼 때와 같은 순서), 커서는 되돌린 글 끝, 포커스(터치 기기도 — 사람이 누른 버튼), 첨부 칩은 그대로. 모듈 저장소라 Files·터미널 탭에 가 있어도 돌아오면 보인다. 응답이 오기 전에 세션을 바꿨으면 넣지 않는다 (입력칸이 세션마다가 아니라 한 벌이라 다른 세션으로 보내게 된다 — 그때 중지로 돌아온 글은 터미널에서도 비워져 사라진다. 응답은 약 0.1~0.5초) unknown 이 아니면 그 세션의 running task 를 실패로 끝낸다. 진행 상태는 메모리에만 있다. **실측 (Claude Code 2.1.307, Haiku)**: 도구 실행 중·글 생성 중 Esc 한 번에 바로 멈춘다 (도구 결과는 "User rejected tool use" 오류 + `[Request interrupted by user for tool use]`, 글 생성 중이면 쓰던 글 + `[Request interrupted by user]`, 화면 "Interrupted · What should Claude do instead?"). **훅은 하나도 오지 않는다** (Stop·PostToolUseFailure 포함, 14종을 걸고 봤다). 입력칸에 쓰던 글이 있어도 Esc 한 번에 멈추고 글은 남는다. 멈춘 뒤 다음 지시는 평소대로 된다
- **작업 중지의 함정.** **응답 첫 글자 전에 Esc 하면 중지 줄이 안 남고 보낸 글이 Claude Code 입력칸으로 돌아간다** — 비우지 않고 화면에서 다음 글을 보내면 입력칸의 글과 이어 붙어 한 번에 제출된다(실측. 그래서 위처럼 비운다. mod 가 안 붙은 세션은 그대로라 화면이 "Terminal tab" 안내를 띄운다). 멈춘 뒤 Esc 는 입력칸을 비우지 않고(실측), Ctrl+U 는 줄 하나만 지운다. **실측 (Claude Code 2.1.312, Haiku, mod 사본 + 기록 서버)**: 돌아올 때 Esc 뒤 약 0.05~0.1초에 `prompt.change` origin `engine`, text = 보낸 글 전체(800자 넘는 붙여넣기 글도 접히지 않은 원문)가 오고, `{ fill: '' }` 로 비우면 origin `plugin` 빈 글이 오며 다음 글은 홀로 제출된다. 도구 실행 중 Esc 에는 입력칸 알림이 없다. 터미널 입력칸에 쓰던 글이 있으면 보낸 글을 되돌리지 않고 중지 줄이 남는다(stopped, 한 번 잼). **돌아온 사람 글 줄은 jsonl 에 남지만 대화에서 빠진다** — 그 줄은 Esc 전, 보낼 때 이미 적힌다 (2.1.307 실측 사본에도 있었다. 예전 "jsonl 에 아무것도 안 남는다" 는 Esc *뒤*에 중지 줄·응답이 안 붙는다는 뜻이었고 버전 차이가 아니다. 실제 jsonl 325개 중 2.1.300~2.1.312 세션 9개에 23줄). Esc 순간에는 아무 줄도 안 붙고, 다음 사람 쪽 줄(다음 글·다시 보낸 같은 글·`/compact`)이 그 줄을 건너뛰어 **같은 parentUuid** 에 붙는다(형제). 되돌린 줄 아래에는 첨부만 있고 응답이 없다. 그 글은 claude 문맥에 없다 (실측: "보낸 메시지를 모두 나열해" 에 되돌린 글이 안 나왔고 압축 요약에도 없었다). `messages.ts` 의 `restoredPromptLines` 가 이 꼴(사람 글 줄 R 뒤에 claude 응답 없이 같은 parentUuid 의 user 줄이 온다. 첫 줄끼리는 둘 다 null)로 그 말풍선을 뺀다 — 서버 메모리가 아니라 jsonl 만 보므로 재시작해도 같다. 실제 jsonl 325개에서 뺀 23줄 모두 어떤 응답의 parentUuid 사슬에도 없었다 (잘못 뺀 것 0). **한계**: 다음 글을 보내기 전에는 가릴 표식이 없어 말풍선이 보인다 (화면은 그 글을 입력칸에 넣으므로 보통 곧 다시 보내 사라진다). 그 사이 서버를 재시작하면 jsonl `turn` 이 in-progress 라 표시 상태가 working 으로 보인다 (다음 훅까지). **다음 글 없이 프로세스가 끝났다 resume 하면** Claude Code 가 그 줄 아래에 "No response requested."(synthetic) 응답을 붙여 그 글이 문맥에 들어간다(실측: 다음 차례 목록에 나왔다) — 응답이 먼저 오므로 빼지 않는다 (그때 웹 입력칸에서 같은 글을 다시 보내면 claude 는 두 번 받는다). `transcript.ts`(`turn`·`turnEndedAt`·제목)는 고치지 않았다: 마지막 사람 줄로 정해 형제가 생긴 뒤에는 R 이 결과를 바꾸지 않고, 제목은 `ai-title` 만 본다. 대기열 짝 맞추기·지시 맞추기도 R 과 무관하다 (R 은 dequeue 뒤 줄이 아니고, 지시 맞추기는 뺀 뒤의 메시지로 한다). **보낸 직후(UserPromptSubmit 훅 뒤 0.1초 안) 중지하면 jsonl 에 그 차례 사람 글 줄이 아직 없어 `isAwaitingFirstResponse` 가 false 다** (시험 서버 실측: 예전 코드면 unknown 이고 글이 터미널 입력칸에 남아 다음 글과 겹쳐 제출됐다) — 그래서 돌아온 글은 응답 전이었는지로 거르지 않고 mod 알림으로 알며, 다른 engine 변경(받아들인 자동완성 등)이어도 비운 글은 화면으로 넘어가 잃지 않는다. 자동완성 목록(`/` 등)이 떠 있으면 첫 Esc 는 목록만 닫고 멈추지 않는다 (두 번째 Esc 에 멈춘다) — 서버는 Esc 를 한 번만 보내므로 unknown 이 된다. 대기 메시지가 있으면 멈춘 뒤 그 메시지로 바로 이어서 일한다 (멈춘 차례의 task 는 실패로 끝낸다). Esc 를 승인 대기·질문 화면에 보내면 거부·거절이라 서버가 막는다. 멈춘 차례에는 `Stop` 의 last_assistant_message 가 없어 `lastAssistantText` 는 앞 차례 것 그대로다

## 확인하지 못한 것

- plugin 이름을 `jk-corp` 에서 `pray` 로 바꾼 것은 가짜 엔진 시험(`claude plugin test mod`)으로만 봤다. 실행 중인 웹 세션이 mod 파일을 다시 읽을 때 이름이 바뀐 plugin 을 그대로 다시 불러오는지(옛 이름을 남기는지)는 보지 못했다 — 반영은 트레이 Quit 상태에서 하므로 새로 뜬 세션은 새 이름만 본다
