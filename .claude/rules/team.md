# 팀·파트·팀장 지휘

팀·파트 판정, 팀장·파트장 지침과 MCP 도구, task 상태 기계, 팀원 이름·모델·effort, worktree 파트를 다룬다. 팀 API 경로 목록은 server-api.md 의 `server/src/index.ts` 항목에 있다.

원래 루트 `CLAUDE.md` 한 파일이던 내용을 옮긴 것이다. 본문의 "위·아래 …"·"핵심 개념 …" 은 그때의 말이라 가리키는 항목이 다른 파일에 있을 수 있다. 어디서나 지킬 규칙·근무·휴식·퇴근·표시 상태·실행 방법은 루트 `CLAUDE.md`, 다른 영역은 루트의 문서 지도를 본다. 이 영역을 고치면 이 파일의 그 줄을 고쳐 쓴다.

다른 파일에 있는 항목:
- 팀 API 경로 목록(`/api/team/*`) → server-api.md
- 세션 이름·역할·성별 저장 규칙 → server-api.md

이름(`claude-sonnet-5-5`)이다. `team_status` 설명은 `contextTokens`·`idleSince` 의 뜻을, `team_dismiss`(서버 `DELETE /api/team/:id/members/:sessionId`)는 그 지휘 단위의 팀원(웹 세션)만 끈다 — 다른 팀·없는 세션 404, 다른 단위 403, 팀장·외부 세션 404 (assign 과 같은 판정). 설명은 lead.ts 의 정리 조건(15만 토큰·60분·영역 일 없음·실패, 문맥 때문이면 요약 넘겨주기, 남이 만든 세션 제외)을 짧게 적는다 — 옛 지침의 리드는 이 설명으로만 새 규칙을 본다. `team_wait` 는 `taskId`(하나)·`taskIds`(여럿 — 그중 먼저 끝난 것. 여러 팀원을 기다릴 때 이것으로 한 번에 부르고 결과의 `pendingTaskIds` 로 다시 부르라는 안내는 도구 설명에 있다)·둘 다 빼면 지휘 단위의 아무 task, 결과 `{ task, pendingTaskIds }`. 기본 1800초·최대 3600초(서버 `taskWait.ts` 의 값과 같다) — 시간 안에 안 끝나면 task null 을 주고 팀장이 다시 부른다. Claude Code 는 120초를 넘는 MCP 호출을 백그라운드로 넘겼다가 끝나면 알림으로 결과를 준다 (팀장 차례는 그 사이 끝나 있다). 그래서 길게 기다려도 팀장이 막히지 않고, 짧으면 null 로 깨어 다시 부르는 차례만 늘어난다. **Claude Code 의 MCP 시간 제한** (2.1.311 바이너리): 벽시계 상한 `MCP_TOOL_TIMEOUT` 기본 1e8ms(약 27.8시간)는 걸리지 않지만, stdio MCP 호출은 응답도 진행 알림도 없이 30분(`CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT` 기본 1800000ms, 서버별 `timeout` 이 더 크면 그것)이 지나면 끊는다 ("sent no response or progress … aborting"). 그래서 `team_wait` 는 Claude Code 가 요청마다 주는 `_meta.progressToken` 으로 60초마다 `notifications/progress` 를 보낸다 — 진행 알림은 jsonl·대화에 남지 않아 토큰이 들지 않는다. 진행 알림 없이 기본 1800초를 기다리면 유휴 한도와 같아 끊긴다. MCP → 서버 fetch(node 내장 undici)의 `headersTimeout`·`bodyTimeout`(각 300초)은 서버가 헤더를 바로 보내고 30초마다 공백을 흘려 걸리지 않는다 (dispatcher 를 바꾸지 않는다 — 내장 undici 의 Agent 는 `undici` 패키지 없이 못 꺼낸다). Claude Code 가 호출을 멈추면(`extra.signal`, TaskStop 등) fetch 를 끊어 서버 기다림도 접힌다. 본문을 받다 끊기면(서버 재시작) "응답을 받는 중 연결이 끊김" 오류가 되고, task 는 파일에 남아(아래 `teamTaskFile.ts`) 다시 부르면 그 결과를 받는다

Stop 훅을 받은 직후라 마지막 응답 줄이 jsonl 에 아직 없으면 그 앞 응답 값이다)를 싣는다 — `team_status`·`team_wait` 결과에도 그대로 보인다. **서버 재시작 때 running 이던 task**(`restore` 로 되살리면 `unreconciled`): 그 사이 훅을 못 받아 그대로 두면 Stop 이 이미 지나간 task 가 영영 running 으로 남아(다음 지시 409·wait 가 시간 초과만 반복) 안전하지 않고, 전부 failed 로 하면 아직 일하는 팀원의 결과를 버린다. 그래서 시작 때(목록을 못 읽으면 5초마다 다시) 한 번 `reconcileRestored` 로 정리한다 (`restoredOutcome`, 순수): 팀원이 근무 중이 아님(목록에 없음·휴식·퇴근) → failed "서버가 재시작하는 동안 팀원 세션이 끝남" (프로세스가 없으니 Stop 이 안 온다. 호스트도 같이 재시작해 resume 된 팀원도 차례가 끊겨 여기다), 근무 중이고 jsonl 마지막 대화 줄 `turnEndedAt` ≥ task `createdAt` 이면 그 차례가 이 지시의 것이라 `turn` 으로 — ended → done(result = 그 차례의 마지막 글), interrupted·cut → failed "서버가 재시작하는 동안 팀원의 차례가 끊김", in-progress → running + 접수됨, 지시 뒤 대화 줄이 없으면 running 그대로 (다음 Stop·접수 시간 초과가 평소처럼 끝낸다). 정리 전에는 `expireUnacknowledged` 가 그 task 를 건너뛴다 (`createdAt` 이 오래돼 바로 failed 가 되는데, 그 사이 접수됐을 수 있다). 정리 전에 Stop 이 오면 평소처럼 끝난다. 사람 지시 차례와 겹치면 그 차례 끝을 task 결과로 보는 것은 평소 Stop 과 같다. 설계: `docs/plans/2026-10-20-team-orchestration-design.md`
- `server/src/teamTaskFile.ts` — task 와 팀원 운영 기록의 파일 `~/.claude/pray/team-tasks.json` (`dataDir()`. hq.json 에 넣지 않는다 — 호스트·서버 공용이라 한쪽 옛 코드가 지울 수 있고, task 는 서버만 쓴다). 꼴 `{ version: 1, tasks: Task[], events: TeamEvent[] }`, tasks 는 넣은 순서(오래된 것 먼저 — `latestOf`·`wait` 가 쓴다). `TeamTaskLog`: 서버 시작 때 `load`(store 에 `restore`), task 가 바뀔 때마다(`onChange`: 지시·접수·끝·가져감·끝 문맥 크기)와 기록을 더할 때 파일 전체를 다시 쓴다 — 같은 폴더 임시 파일(`team-tasks.json.<pid>.tmp`) → `renameSync`(EPERM·EBUSY·EACCES 50ms 5번, hq.ts 와 같다). 쓸 때마다 보관 기간 정리: 끝난 task 는 `finishedAt` 7일(`TASK_RETENTION_MS`), 운영 기록 30일(`EVENT_RETENTION_MS`, 한 줄이 작아서), 경계 시각은 남기고 running 은 지우지 않는다. **던지지 않는다** (훅·타이머·호스트 이벤트에서 불린다): 저장 실패는 로그 한 줄(실패·복구로 바뀔 때만)이고 메모리는 그대로, 파일이 없으면 빈 상태, 못 읽거나 깨졌으면 로그를 남기고 빈 상태로 시작하며 깨진 파일은 `team-tasks.json.broken-<시각>` 으로 옮겨 둔다 (다음 저장이 덮어쓰지 않게). 항목 하나의 꼴이 틀리면 그 항목만 버리고, 나중에 더한 칸이 없는 옛 항목은 null 로 채운다. **운영 기록 `TeamEvent`** `{ kind: spawn·dismiss, at, teamId, partId, sessionId, position, model, effort, contextTokens, idleSince }` — 팀원 정리 기준(15만·60분)을 실제 값으로 맞추려고 남긴다 (화면은 팀 Tasks 창 → 아래 `teamTaskHistory.ts`). spawn = 팀원 spawn API 가 호스트에 보낸 뒤(팀장이 고른 model·effort 별칭, 빼면 null. contextTokens·idleSince 는 새 세션이라 null), dismiss = `team_dismiss` 가 kill 을 보내기 직전 세션 목록 값(model 은 jsonl 의 전체 이름, partId 는 확인한 지휘 단위. 그 단위의 팀원이 아니면 기록도 kill 도 하지 않는다). 화면 종료 버튼(dismissed)은 남기지 않는다. 테스트 `teamTaskFile.test.ts`

## 핵심 개념

- **팀원은 역할별로 오래 두고 다시 쓴다** (lead.ts 지침의 배치·재사용·정리 규칙). 영역에 할 일이 처음 생기면 그 role 팀원을 만들고(영역별 1명, 동시에 최대 3명 — 같은 작업 트리라 파일이 겹치지 않게), 사용자 요청이 바뀌어도 같은 영역이면 있는 팀원에게 `team_assign` 한다 (이미 읽은 지침·코드를 다시 읽지 않아 싸다. 조사 팀원도 후속이 있을 법하면 둔다). 정리는 `team_status` 로 보고 하나라도 맞으면 한다: `contextTokens` 15만 초과(단계마다 문맥 전체가 다시 들어가 비싸고, 더 커지면 자동 압축으로 세부가 흐려진다), `idleSince` 부터 60분 넘게 쉼(프롬프트 캐시가 끝나 다음 지시 때 문맥 전체를 캐시 없이 다시 낸다), 계획에 그 영역 일이 더 없음. 문맥 때문에 정리하면 먼저 그 팀원에게 "알게 된 것·고친 파일·남은 일" 요약을 받아 새 팀원 첫 지시에 붙인다. 사용자 승인을 기다리는 동안은 유지(수정은 쓴 팀원이), 실패·엉뚱한 방향이면 정리하고 지시를 고쳐 새로 만들고, 남이 만든 세션은 정리하지 않는다. 지침은 새로 만든 리드부터 적용되고, 옛 지침의 리드는 claude 가 다시 뜬 뒤(resume 포함) `team_status`·`team_dismiss` 도구 설명으로만 본다 (위 lead.ts·mcp)
- **팀장 지시(`assignTask`·팀원 첫 지시)는 지시문과 Enter 를 따로 보낸다** (`submitInstruction`: 지시문 전송 → 그 세션의 pty 출력이 700ms 동안 없으면 `\r`, 출력이 계속 나와도 8초가 지나면 `\r`). 한 번에 보내거나 고정 간격(300ms~2초)으로 보내면 긴 지시문을 Claude Code TUI 가 붙여넣기로 처리하는 동안 `\r` 이 흡수돼 입력창에 남고(`[Pasted text #1 +1 lines]`), UserPromptSubmit 이 안 와 task 가 failed 가 된다. 그래서 접수 판정 `ACK_TIMEOUT_MS` 는 Enter 최대 대기 8초 + 5초 = 13초
- **팀원 jsonl 에서 지시는 사람 입력과 똑같은 user 메시지(`origin.kind: human`)라서, 서버가 보낸 지시를 `~/.claude/pray/instructions.jsonl` 에 따로 남기고(`{ sessionId, fromSessionId, text, at }`, fromSessionId 는 그 지휘 단위의 팀장·파트장) 내용으로 맞춘다.** 비교는 붙여넣기 태그와 공백을 전부 무시하는 키(`instructionKey`)로 하고 (긴 지시는 붙여넣기로 감싸여 저장된다. 푸는 규칙은 `messages.ts`), 맞으면 글을 보낸 지시문으로 바꿔 준다. 기록 파일은 계속 쌓이기만 한다
- **지시자 인계: 새 팀장·파트장이 직전 지시자의 히스토리를 첫 메시지로 받는다.** 세션 추가 모달에서 Lead·Part lead 를 고르면 `POST /api/sessions` 에 `carryOverHistory: true`(boolean 이 아니면 400). 살아 있는 지시자가 있으면 409 라 직전 지시자는 늘 끝난 세션이고, 서버가 `leadSessionId` 를 새 ID 로 바꾸기 전에 직전 ID 를 잡아 둔다. spawn·응답 뒤 `handOverHistory` 가 직전 지시자 jsonl(`findTranscriptFile`)을 줄 단위 스트림으로 읽어 인계 글을 만들고, spawn 뒤 4초(`MEMBER_FIRST_INPUT_DELAY_MS`, jsonl 읽기와 겹친다)에 팀원 첫 지시처럼 `submitInstruction` 으로 보낸다. jsonl 이 없거나 글이 비면 아무것도 안 보낸다. 첫 메시지는 claude 가 읽는 글이라 한국어: "아래는 이전 팀장(<이름>) 세션의 요약이다. 숙지하고 '인계받음' 한 줄로만 답하라" + 본문(파트장은 "이전 파트장", 이름은 역할 없이 `displayNameOf`). **`--append-system-prompt` 에 넣지 않는 이유**: extraArgs 로 hq.json 에 영구 저장되고 Windows 명령줄 32,767자 제한에 걸린다. **instructions.jsonl 에 `fromSessionId` = 직전 지시자로 남긴다** — 안 남기면 새 지시자 대화에 사람이 쓴 긴 글처럼 보이고, 남기면 "Instruction from <직전 지시자>" 지시 말풍선이다 (팀원 task 와는 무관). **본문**: 직전 jsonl 의 마지막 압축 요약(`isCompactSummary` 줄. 꼬리 "Continue the conversation from where it left off…" 부터 끝은 같은 세션을 이어 가라는 지시라 뗀다) + 그 뒤 주 대화 차례마다 사람 지시(user 글·`queued_command`, 붙여넣기 감싸기는 푼다)와 그 차례의 마지막 claude 글만. 빼는 것은 `transcript.ts` 의 차례 규칙과 같다(도구 호출·결과·사이드체인·메타·`<` 로 시작하는 글·중지 줄·`<synthetic>`). 배열 글은 `<` 로 시작하는 text 블록도 뺀다. **압축 때 요약 대신 그대로 남긴 최근 메시지**(`compact_boundary` 의 `compactMetadata.preservedMessages.uuids`)는 jsonl 에서 경계 앞에 있어 그 uuid 의 글을 요약 뒤 차례 맨 앞에 남긴다. 압축이 한 번도 없으면 차례만. 사람 글이 앞선 인계 메시지("아래는 이전 팀장(" 로 시작)면 그것을 요약으로 쓰고 그 답("인계받음")은 뺀다 — 압축 없이 다시 바뀐 지시자에게 그 이전 히스토리가 이어지게. **상한**(`HANDOFF_LIMIT` 4만 자, 머리말 빼고): 요약을 먼저 다 넣고(요약만으로 넘으면 앞부분만) 남은 자리에 최근 차례부터 거꾸로 채워 앞 차례를 자르고 "앞 글 N개 생략" 을 적는다. 차례 글 하나는 4천 자(`HANDOFF_ITEM_LIMIT`)에서 자른다 (붙여 넣은 로그 하나가 상한을 다 쓰지 않게). 큰 줄(api-request·도구 결과)은 `"type":"user"` 같은 글자가 없으면 JSON.parse 하지 않는다. 실측: 213MB jsonl(압축 12번) 약 0.8초·인계 글 1만 4천 자(요약 1만 2천), 89MB(압축 없음) 0.3초. (broadcast 마다라 projects 를 훑지 않는다. 지시자가 살아 있어도 true 다 — 그때는 Lead 세그먼트가 비활성). 화면은 그 단위에서 Lead·Part lead 를 골랐고 true 일 때만 칸을 보인다 (→ web-app.md)
- **파트 = 팀 안의 선택적 지휘 단위.** 지휘 단위(팀 직속 또는 파트)마다 지시자 한 명: 팀장은 팀 직속(파트 없는 세션)만, 파트장은 자기 파트만 지휘하고 2단 지휘는 없다. 소속 판정: worktree 파트는 **폴더로**(그 worktree 폴더의 세션은 외부 세션도 자동 합류. `teamOf` 도 파트 worktree 폴더를 그 팀으로 본다), 팀 폴더 세션은 `teams[].partOf` 기록으로, 둘 다 없거나 기록이 지워진 파트를 가리키면 팀 직속. 팀장·파트장과 worktree 세션은 소속 이동(`PUT /api/team/:id/partOf/:sessionId`)을 거부한다
- **worktree 파트**는 서버가 저장소 옆 `<저장소>.worktrees/<슬러그>` 에 브랜치 `part/<슬러그>`(현재 HEAD 기준)로 만들고 `~/.claude.json` 의 `projects["<경로>"].hasTrustDialogAccepted = true` 를 기록한다 (사용자가 승인한 자동 기록. 이것으로 신뢰 확인 창이 안 뜨는 것을 확인함). 쓰는 규칙은 위 세션 폴더 신뢰와 같다 (해석에 실패하면 화면이 경고). **그 자리에 이미 있으면 연결한다**(`isLinked: true`, 화면은 알림 창으로 알림): 이 저장소의 worktree 면 새로 만들지 않고 그 폴더와 **그 worktree 의 브랜치**(`part/…` 가 아니어도)로, 브랜치 `part/<슬러그>` 만 있으면 `git worktree add <폴더> part/<슬러그>`(-b 없이 — HEAD 가 아니라 그 브랜치 내용)로. 등록만 남고 폴더가 지워진 worktree 는 그 등록을 지운 뒤(`worktree remove`, 그 항목만. `prune` 은 다른 worktree 까지 건드려서 안 쓴다) 브랜치만 있는 경우로 간다. 409: 폴더가 있는데 이 저장소의 worktree 가 아님, detached worktree, **다른 파트(어느 팀이든)가 쓰는 폴더**(두 파트가 한 폴더를 쓰면 폴더로 정하는 소속이 깨진다. `api`·`API` 처럼 슬러그가 같은 이름). **파트를 지우면 worktree 폴더와 브랜치도 지운다** (병합은 사람이 한다). 먼저 확인만 하고 걸리면 아무것도 안 지운다: 그 폴더 **또는 하위 폴더**에서 근무 중인 세션(호스트 목록·살아 있는 pid 기록의 cwd) → 409 "End the sessions in the worktree folder first" (하위 폴더도 막는 이유: Windows 에서 폴더를 현재 폴더로 쥔 프로세스가 있으면 `git worktree remove` 가 파일과 등록은 지우고 폴더만 못 지운 채 실패한다(실측). 그래서 Pray 세션이 아닌 프로세스·편집기가 쥐고 있으면 여전히 그렇게 된다), 커밋하지 않은 변경(`status --porcelain`, 추적 안 하는 파일 포함) → 409, 브랜치가 팀 폴더 HEAD 에 병합되지 않았는데(`merge-base --is-ancestor`) `?branch=` 가 없으면 → 409 branch-unmerged, git 이 상태를 못 읽으면 → 409. 통과하면 `git worktree remove`(폴더가 이미 없으면 등록만 지운다. 이 저장소의 worktree 가 아닌 폴더는 건드리지 않는다) → 브랜치(병합됨 `-d`, 병합 안 됨 + `delete` 는 `-D`, `keep` 은 병합됐어도 남김) → 파트 기록. 중간 실패는 거기서 멈추고 한 일을 알린다: worktree 를 못 지웠으면(등록이 남음) 기록도 남기고, worktree 가 없어졌으면(폴더만 남음·브랜치 삭제 실패) 기록은 지운다. 휴식·퇴근 세션은 막지 않는다 (다시 출근하면 폴더가 없어 거절되고, 호스트는 폴더가 없는 휴식 세션을 건너뛰며 지운다)
